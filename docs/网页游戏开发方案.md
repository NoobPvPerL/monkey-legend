# 《应猴传说：高唐之战》网页游戏开发方案

日期：2026-10-13。状态：方案草案，尚未开始游戏实现。

依据：已完整读取 `rule.md`，并通过分组预览浏览六个素材目录的全部 187 张图片。以下是素材盘点与开发建议，不等同于逐张卡牌完成规则转录、数值校对或原作者确认。

## 1. 项目目标与推荐路线

将现有桌游改编为浏览器里的多人回合制卡牌战棋游戏，保留校园地点、角色技能、行动点、随机判定、阵营战、各自为战、轰炸区和毒圈等特色。

推荐分为四步：规则整理与确认 → 本地完整对局 → 好友房间联机 → 全量内容扩展。

先通过少量原作角色和卡牌验证一局能否正确开始、推进、淘汰和结束，再按机制分批接入其他内容。首版暂不启用的卡牌必须在牌池中明确排除，不能展示为可用却没有实现效果。

建议把四人测试桌作为第一轮验收场景，验证各自为战和 2 对 2 阵营战；四人仅是开发建议，正式人数范围需由原作者确认。规则架构应支持不同人数，界面与服务器容量在确认后定标。

| 角色牌 | 58 | 初步识别为 53 张有文字角色牌、1 张模板、4 张阵营相关图像 | 角色选择、技能说明、阵营视觉 |
| 神牌 | 18 | 16 张有文字的角色式神牌、1 张空白模板、1 张牌背 | 特殊角色与死亡触发机制 |

素材原始总量约 61.4 MiB。多数基础牌与角色牌为 720×1280 图片，文字已嵌在图内。浏览器实际操作应另外提供可缩放的文字说明，原图用于收藏式详情和原作对照。工程内使用稳定的英文 ID 与素材映射，不依赖相机文件名作为业务标识；原始文件保留。

已明确的基本规则：

- 三种角色阵营：机械猴子、帝汶家族、中立阵营。
- 两种玩法：阵营战、各自为战。
- 4 行 8 列、32 个地块；地块被划分为不规则区域，存在水域、普通地面与特殊地块。
- 角色在固定出生区出生，移动和主动技能涉及行动点。
- 行动点初始 3 点，每回合增加 2 点；角色与牌面存在例外。
- 初始手牌 4 张，后续每一轮行动前抽 1 张。
- 存活到最后的阵营或个人获胜，并按淘汰次序产生排名。
- 移动、命中、技能和环境事件存在受规则约束的随机判定。

需要避免混淆：角色所属阵营、当前阵营、对局队伍分别建模。中立角色可以加入双方队伍；“化汉”“化猴”改变阵营后是否改变队伍和胜利归属，不能由程序自行推断。

## 3. 实现前必须补全的规则

### 3.1 第一批阻塞项：基础对局

| 问题 | 当前资料的缺口 | 需要产出的确认结果 |
|---|---|---|
| 人数与选角 | 未规定人数、抽几张角色再选、是否可重复角色、先后手 | 开局流程与可选人数 |
| 阵营与队伍 | 角色牌未全部直接注明阵营，中立角色的分队方式不完整 | 每个角色的阵营表、队伍分配与变阵营规则 |
| 回合与轮次 | “回合”“一轮”混用，抽牌与环境结算时点不清 | 单人回合与全桌轮次定义 |
| 行动点 | 无通用上限、是否保留剩余点数、首次行动是否再加 2 点 | 增加、上限、结转和首次行动规则 |
| 移动 | 未说明消耗多少、骰子点数怎样变步数、方向与路径选择、越界与占位 | 完整移动规则，含被动移动与传送 |
| 距离与区域 | “同格”“相邻格”“相同/相邻区域”的关系不同 | 邻接算法、是否含斜角、距离算法 |
| 牌堆 | 图片未给出每种牌的实体份数、抽空后处理和手牌上限 | 牌池份数、弃牌与洗牌规则 |
| 地图 | 地图图像没有标出 32 格坐标及各格所属区域 | 4×8 坐标表、区域表、出生区与通行表 |
| 地形 | 地点插画没有完整描述地点、水域、特殊地块效果 | 地形效果、触发时机和区域容纳人数 |
| 天灾 | 未给出候选区域、缩圈进程、轰炸/毒圈伤害与持续时间 | 环境事件表和全部概率 |
| 通用判定 | 很多牌写单数、双数、1—6，但总规则没有定义骰子 | 骰子种类、各面概率、重掷/指定点数优先级 |
| 淘汰结算 | 未写同时死亡、无人存活、救援与最终胜利的关系 | 淘汰、平局、救援窗口与胜利时点 |

### 3.2 接入复杂牌之前确认的裁定

- **响应时机与优先级。** “肘击”响应“头锤”，“防御姿态”抵挡普通牌，“第三只手”抵消锦囊，“最高等级”和“无视”之间的关系需要统一定义。建议整理为裁定表，由原作者确认。
- **连锁触发。** 猴四受伤回出生地并免伤；土豆受伤可传送；正装反伤；北帝汶免疫部分牌。必须明确扣血、护盾、反伤、受伤技能、传送和死亡谁先发生，以及一次事件能触发几次。
- **插队。** `assets/cards/基础牌/锦囊-建民-插队.png` 明确涉及跳到自己回合、刷新回合次数并确定轰炸区与毒圈；需要定义被中断回合如何恢复、轮次是否增加、抽牌与行动点是否重置。
- **改阵营与特殊胜利。** `assets/cards/基础牌/锦囊-神秘-化汶.png`、`assets/cards/基础牌/锦囊-神秘-化猴.png` 改阵营；应豪、东帝汶等角色还存在集齐或打出组合即可胜利的技能。胜利判定需要可扩展的条件集合。
- **死亡与复活。** “紫檀木”能复活刚死亡角色；神牌含“神的陨落”效果，Q 博等还有类似觉醒或保命效果。生命归零应进入待结算状态，处理允许的救援与触发后再确认淘汰和最终胜利。
- **可变费用。** 多张牌写 `1/2/3`、`4/5/6`、`1—6`，有的还出现负费用；需要解释由谁或什么决定费用，何时确定，是否可能取消或返还。
- **技能费用缺失。** 总规则说释放技能耗行动点，但部分主动技能未写费用；不能统一补成 1 点。
- **选修课。** 说明图包含冷却、半点生命、百分比减伤/暴击、复活和传送，但未给出获得渠道、装备数量及与角色技能的关系。“天道伤害”需与毒圈、轰炸、直伤的定义对应。
- **未知参数。** 三幻神的出生地标作 `???`，猴五生命上限与其他无上限/自定义判定角色也需要专门表达。

建议让原作者用两三局真实对局讲解，记录有代表性的“先后结算”案例。将每个结论标为“原作已确认”“原作者补充”“网页版提案”或“仍待确认”，避免把技术上的处理习惯写成原规则。

## 4. 网页体验设计

核心流程：创建/加入好友房间 → 设置模式 → 准备与选角 → 出生和发牌 → 顺序行动及响应 → 环境推进 → 淘汰/复活 → 胜利与排名 → 再开一局。

建议的桌面布局：

```text
┌─────────────────────────────────────────────────────────────┐
│ 轮次 · 当前行动者 · 模式 · 环境提示 · 连接状态                │
├───────────────┬──────────────────────────┬──────────────────┤
│ 玩家与队伍    │                          │ 所选角色/地块    │
│ 血量/护盾     │        4 × 8 棋盘        │ 原图与文字说明   │
│ 行动点/状态   │ 区域边界、棋子、路径预览 │ 裁定与战斗日志   │
├───────────────┴──────────────────────────┴──────────────────┤
│ 自己的手牌 · 移动 · 技能 · 装备/坐骑 · 结束回合              │
└─────────────────────────────────────────────────────────────┘
```

地图使用原图作为视觉背景，叠加明确的 32 格、区域边界、地形图标与坐标。规则上的区域归属通过数据配置，不依赖背景图像识别。根据原作者确认的坐标表调整映射，不能仅把图像等分后认定地形。

出牌建议采用“点击牌 → 展示说明与费用 → 高亮合法目标 → 选择目标 → 提交”。移动建议采用“选择移动 → 按规则判定步数 → 选择允许的方向/路径 → 提交”；具体先选方向还是先摇骰由原规则决定。

需要玩家选择的防御或技能弹出响应面板，明确谁在响应、可选动作、费用和结果。响应期间阻止无关动作。没有可用响应时自动继续；需要多个玩家响应的群体牌，按确认的顺序安排。

界面显示判定值、修改原因和最终效果，例如“单数命中 → 被免疫 → 未扣血”，方便原作者核对。自动锁定技直接结算，可选被动技要让玩家决定，不能自动替玩家使用。

视觉建议沿用已有地点插画和蓝色/金色卡牌元素，棋盘与信息区域降低装饰强度，以可读性为主。不同队伍用颜色加图标区分。原有图片详情可放大；实际手牌缩略图突出名字、费用、类型和关键效果。

桌面先验收，随后适配平板与手机横屏；手机竖屏采用可切换的信息面板与手牌抽屉，并专项验收点击目标、阅读文字与响应操作。

## 5. 技术方案

### 5.1 推荐组合

| 层 | 推荐 | 目的 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 卡牌、房间、响应面板和详情组件；统一规则类型 |
| 棋盘 | HTML/CSS Grid + SVG 覆盖层 | 32 格点击、区域边界、路径和危险区提示 |
| 规则 | 独立 TypeScript 模块 | 本地试玩与联机服务器复用同一套逻辑 |
| 服务端 | Node.js + Socket.IO | 房间、身份恢复、顺序命令处理与实时同步 |
| 数据 | JSON 定义；联机阶段用 SQLite 保存快照和事件 | 牌池、角色、地图、规则版本和故障恢复 |
| 验证 | 规则单元测试 + Playwright 浏览器测试 | 裁定、完整对局与多客户端同步 |

这是针对当前 32 格、文字卡牌和回合制交互的工程选择。首版棋盘无需复杂绘制引擎；若后续增加大量实时动画，可单独引入 Canvas 层，不影响规则引擎。

React 官方文档描述组件化界面；Vite 官方提供 React TypeScript 模板。Socket.IO 负责传输，但消息默认并不保证断线后补发，因此命令确认、去重、状态版本和重连快照应在游戏层实现。Playwright 可用于 Chromium、Firefox、WebKit 及 Chrome/Edge 的界面验证。

参考：[React 组件](https://react.dev/learn/your-first-component)、[Vite 入门](https://vite.dev/guide/)、[Socket.IO 投递保证](https://socket.io/docs/v4/delivery-guarantees/)、[Playwright 浏览器支持](https://playwright.dev/docs/browsers)。实施时检查运行环境并锁定兼容版本，不在方案中预设未经验证的版本号。

### 5.2 规则引擎与结算

规则引擎与 UI、网络、系统时钟分离，接收“游戏状态 + 玩家命令 + 受控随机输入”，返回新状态、事件和待响应事项。命令包括移动、出牌、技能、选择响应、结束回合等。

状态至少包含：规则版本、模式、轮次、当前行动者、玩家队伍与阵营、角色属性、地图地形、牌堆/弃牌堆、卡牌实例、装备、坐骑、持续状态、环境事件、待处理效果、待响应玩家与淘汰记录。

卡牌定义和实体卡分开：一种“躲避球”使用一个定义 ID，多份实体卡各有实例 ID。角色也将初始属性与对局中变化的属性分开。图片只是显示资源，不能承担逻辑。

以通用效果处理抽牌、弃牌、行动点增减、伤害、治疗、移动、传送、免疫、状态和地形变化；组合复杂的角色用专用处理器。不要执行卡牌文本中的任意代码，也不要把 100 多种效果堆进一个界面函数。

普通行动的建议框架如下，详细顺序仍需原作者确认：

```text
检查阶段/操作者/合法目标
  → 确定与支付费用、提交卡牌
  → 打开适用的响应窗口
  → 判定与修正
  → 按裁定顺序处理效果、移动、伤害及触发
  → 处理救援、生命归零与死亡触发
  → 确认淘汰并检查胜利
  → 恢复行动或进入下一阶段
```

连锁效果放入队列，记录来源与已经触发的能力，防止同一事件被重复处理。必须区分个人回合开始/结束和整轮开始/结束，让“到下回合”“每轮一次”“跳过回合”能准确表达。

随机数仅由本地规则实例或联机服务器生成。固定种子用于测试复现；联机时不提前把种子、未来骰子和牌堆顺序传给客户端。实际判定事件按可见范围记录。

选修课存在 0.5 点血及百分比效果，建议内部用固定精度整数记录生命与伤害，按已确认规则取整；展示转换为小数，避免浮点误差。基础版也提前使用同一数值模型，减少以后迁移。

### 5.3 联机与隐藏信息

- 客户端提交操作意图，服务器验证并作最终裁定；客户端不能提交“我造成 3 点伤害”作为可信结果。
- 同一房间的命令串行处理，携带命令 ID 和状态版本；重复命令返回原结果，旧版本命令拒绝并重新同步。
- 服务器发送每个玩家专属视图：自己的手牌内容、他人的手牌数量、公开棋盘与状态。牌堆顺序、别人的手牌和私密选择不发给无权查看者。
- 重连使用房间身份凭据，恢复同一座位并获取快照；完整状态与待响应事项保存到服务端，避免页面刷新造成对局变化。
- 响应超时、掉线宽限与长时间离开后的处理，需要作为网页版规则确认。首版建议提示并允许有限暂停，不直接默认为机器人接管。
- 单实例服务器即可作为好友测试起点；达到真实并发需求后再做多实例扩展。公网部署使用 HTTPS/WSS，并确保房间进程可长期运行。

## 6. 分阶段实施与验收

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| P0 规则整理 | 32 格地图表、角色阵营表、牌池份数、回合流程、裁定清单、卡牌登记表 | 原作者确认首版所需规则；未确定项明确隔离 |
| P1 本地完整对局 | 4 人测试桌、两种胜利策略、4—6 个已核对角色、12—16 种基础牌、完整地图和已确认环境规则 | 能从开局打到胜利；与手工裁定案例一致；可复现判定 |
| P2 好友联机 | 建房、加入、准备、选角、私密手牌、响应、重连和结算 | 多浏览器/多设备共同完成一局；重发不重复扣费；刷新不丢座位、不泄露手牌 |
| P3 内容扩展 | 按机制分批接入角色、装备、坐骑、锦囊与特殊胜利 | 每张已启用牌都能正确使用；复杂连锁和排名通过核对 |
| P4 神牌与选修课 | 死亡触发、复活、觉醒、课程来源/冷却/百分比机制 | 相关完整对局案例一致，无连锁循环与提前结算 |
| P5 发布准备 | 响应式 UI、素材加载优化、操作说明、部署包、回归与试玩报告 | 原作者及朋友真实试玩通过；公网多设备验收后再对外发布 |

P1 同屏轮流操作适合调试和规则核对，会存在同设备窥视手牌的局限；正式好友体验以 P2 的独立客户端为准。可提供交接遮罩减少误看，不能把同屏模式当作已经实现私密联机。

P1 的少量牌池由原作者确认，建议覆盖单体攻击、群体攻击、治疗、防御响应、抽弃牌和简单位移，选取文字与费用已清楚的原作内容。“躲避球”“吸血”“防御姿态”“外星人”等可作为候选。高级免疫、任意时点插队、临时变阵营、复活、无限/自定义属性的内容待相关机制成熟后启用。

P3 不按文件夹顺序硬塞内容，按机制分批上线：基础伤害与治疗 → 装备与坐骑 → 控制/抢牌/地形 → 回合修改/改阵营/组合胜利。首版角色的某项技能若依赖尚未启用机制，应更换首版角色，不删掉技能后冒充完整角色。

## 7. 验证重点

1. 原作一致性：用明确的手牌、位置、血量和指定判定值，逐步对照原作者裁定。
2. 空间规则：32 格、出生、路径、区域邻接、水域通行、强制移动和传送落点。
3. 状态生命周期：回合开始抽牌/加点、状态到期、装备次数、跳过回合与整轮环境更新。
4. 伤害与连锁：免疫、护盾、反伤、真实伤害、半点生命、受伤移动、救援、复活与神牌死亡触发。
5. 胜利与排名：最后一人/一队、特殊胜利、同时淘汰、改阵营、复活后排名处理。
6. 联机：多个客户端同状态、私密牌、重复命令、断线重连、刷新、待响应阶段恢复。
7. 操作可用性：合法目标提示、错误原因、可读卡牌、当前玩家状态和手机目标选择。

只有实际完成并记录的检查才能标记“通过”。本方案阶段没有构建游戏，没有运行游戏测试，也没有发布网站。

## 8. 工作量与决策建议

规则和素材校对是当前最大的未知项。粗略按一名熟悉 TypeScript 的开发者估算，在首版规则及时确认、没有新增美术的前提下：P0 约 2—5 个工作日，P1 约 5—8 日，P2 约 5—8 日；首个好友联机小版本约 12—21 个工作日。全量复杂内容与发布准备另需约 3—6 周或更长，主要取决于原作裁定数量和试玩修改。这是排期估算，不是交付承诺。

第一轮只需先确定三组信息：

1. 首个版本主要面向电脑还是手机，目标人数多少；是否接受先用四人测试桌验收。
2. 能否由原作者给出 4×8 地图标注，以及行动点、移动、牌堆和天灾的基础规则补充。
3. 是否接受先做少量完整原作内容的好友联机版本，再扩充神牌和选修课；首版内容由谁确认。

建议批准 P0 的规则整理范围后先产出可审阅的规则规格、素材登记与首版牌池。P0 通过后进入实现，后续每阶段以交付物和实际验收记录决定是否继续扩大范围。
