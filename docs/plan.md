## 2. 首版范围与排期前提

以下是规划建议，尚未作为原作规则或已批准需求：

- 第一轮以 4 人测试桌验收，覆盖各自为战和 2 对 2 阵营战。
- 先接入 4—6 个完整角色、12—16 种基础牌；数量与具体名单在 P0 确认。
- 覆盖完整 32 格地图、已确认的地形和环境规则、开局到胜利的完整流程。
- 先验证本地对局，再接入每人独立浏览器的好友房间。
- 首版优先桌面浏览器；手机目标与适配优先级在 P0 确认。
- 神牌、选修课和复杂回合干预机制分批实现，暂未支持的内容从可选角色与牌池中排除。

排期按一名熟悉 TypeScript 的开发者、规则反馈及时、复用现有美术估算。采用有效工作日，不设未经确认的开工日期；等待规则反馈的时间另计。P0 完成后重估，以下工期不构成交付承诺。

## 3. 阶段总览

| 阶段 | 目标 | 预计有效工作日 | 主要依赖 | 阶段完成标志 |
|---|---|---:|---|---|
| P0 | 规则规格与首版内容确认 | 2—5 | 原作资料、用户/原作者裁定 | 首版无未决的必要规则 |
| P1 | 本地完整可玩版本 | 5—8 | P0 首版规格通过 | 能正确完成两种模式的测试对局 |
| P2 | 好友房间联机版本 | 5—8 | P1 规则引擎与完整对局通过 | 多设备完整对局、私密手牌及重连通过 |
| P3 | 基础牌与普通角色扩展 | 7—14 | 对应复杂规则已确认、P2 稳定 | 所有本阶段启用内容实现并验证 |
| P4 | 神牌与选修课 | 5—10 | 死亡、复活、课程等规格确认 | 特殊机制对局与连锁案例通过 |
| P5 | 体验完善、试玩与发布准备 | 3—6 | 内容范围冻结、P3/P4 通过 | 真实试玩和发布验收完成 |

里程碑：P0 累计约 2—5 日；P1 累计约 7—13 日；首个少量内容好友联机版本 P2 累计约 12—21 日。P3—P5 合计另需约 15—30 日；全部阶段约 27—51 个有效工作日，复杂裁定或试玩调整可能增加工期。

依赖顺序：`P0 → P1 → P2 → P3 → P4 → P5`。响应式界面、素材优化和复杂牌的文字校对可提前准备；其验收仍归入对应阶段。准备工作无需等待所有高级规则明确，但依赖未决规则的效果实现与正式验收必须等待确认。

## 5. P1：本地完整可玩版本

推荐技术路线沿用已有方案：React + TypeScript + Vite；棋盘使用 CSS Grid 与 SVG；独立 TypeScript 规则引擎。具体依赖版本在实施时核对与锁定。

### P1.1 工程与数据

- [ ] 检查现有 Git 项目、开发环境与工具，建立前端、规则、数据和测试目录。
- [ ] 建立角色/卡牌定义、卡牌实例、地图、规则版本和素材映射。
- [ ] 增加资料校验，检测缺失字段、错误引用、无效地图坐标和未确认内容误入牌池。
- [ ] 保留原始素材，仅生成浏览器所需的衍生资源。

### P1.2 对局规则引擎

- [ ] 实现开局、选角、出生、洗牌、初始 4 张手牌和初始 5 点行动点。
- [ ] 按 P0 规格实现整轮统一条件加点、首轮不补、补牌/弃牌、环境与个人行动；待补牌对象等必要缺口明确后实施。
- [ ] 实现移动、合法目标、主动技能、随机判定、受控测试随机输入及事件日志。
- [ ] 实现首版攻击、治疗、防御响应、抽弃牌和位移效果。
- [ ] 实现效果队列、状态到期、触发记录，以及后续死亡/复活扩展接口。
- [ ] 实现已确认的地形、轰炸、毒圈与缩圈规则。
- [ ] 实现淘汰、排名及两种模式的胜利条件。

### P1.3 操作页面与本地试玩

- [ ] 完成 32 格棋盘、区域边界、棋子、地形和危险区显示。
- [ ] 完成角色详情、手牌、费用、技能、合法目标、响应面板与结束回合。
- [ ] 提供判定与效果日志，解释失败、免疫、扣血和移动原因。
- [ ] 完成本地轮流操作和交接遮罩，支持重新开局与测试场景载入。
- [ ] 提供 Windows 本地启动说明及启动入口。

### 验收与交付

交付本地可玩版本、首版内容表、启动说明和实际测试报告。分别完成各自为战与阵营战的完整测试对局；用指定判定值与手工裁定逐步对照。

重点验证非法操作不改变状态、费用只扣一次、回合与状态期限正确、角色技能完整、环境正确推进、排名与胜利一致。本地交接遮罩只能减少误看，不计作私密联机验收。

## 6. P2：好友房间联机版本

服务端推荐 Node.js + Socket.IO，复用 P1 规则引擎；持久化对局快照与事件，初期采用单实例服务。

### 工作清单

- [ ] 实现昵称、建房、房间码、加入、准备、模式设置、选角与重新开局。
- [ ] 建立房间座位、队伍、对局身份凭据和生命周期。
- [ ] 由服务端处理合法命令、抽牌、骰子、触发与最终裁定。
- [ ] 为玩家生成专属视图，只显示自己的手牌内容和他人的公开信息。
- [ ] 同房间命令串行处理，增加命令 ID、确认、去重和状态版本。
- [ ] 同步待响应玩家及可选操作，防止多客户端重复结算。
- [ ] 持久化状态与事件，实现刷新/短暂掉线后的座位、快照和响应恢复。
- [ ] 确认响应超时、掉线宽限、长时间离开后的网页版处理规则，再实施。
- [ ] 提供多客户端测试入口与开发部署说明。

### 验收与交付

交付好友联机小版本和联机测试报告。多个独立浏览器/设备完成一局，公开状态一致；检查网络数据中不含他人手牌、未来骰子或牌堆顺序。

验证重发命令不会重复扣费/出牌，旧状态操作会被拒绝并同步；刷新、断线和响应中重连可恢复同一座位。自动化多客户端检查与朋友真实多设备试玩分别记录，不能互相代替。

## 7. P3：基础牌与普通角色扩展

按机制分批接入，每批采用“文字与裁定确认 → 数据登记 → 效果实现 → 组合案例 → 对局试玩”的顺序。

1. 基础伤害、治疗、抽弃牌及普通角色技能。
2. 装备槽、装备次数、装备替换/丢失触发和坐骑。
3. 控制、抢牌、传送、强制移动与地形变化。
4. 插队、跳过回合、改阵营、组合胜利、复活等复杂内容。

- [ ] 确认“最高等级”、无视、免疫、抵消与反伤的裁定关系。
- [ ] 确认插队后的回合恢复、抽牌/行动点和环境推进。
- [ ] 区分角色初始阵营、当前阵营与对局队伍，确认变阵营后的胜利归属。
- [ ] 处理普通牌中的复活和角色保命，验证救援窗口与最终胜利的关系。
- [ ] 逐批维护已实现、待确认、暂不支持的内容清单。

验收：本阶段每个启用角色的全部技能及每张启用牌都具有验证证据；通过费用、目标、触发、状态到期及代表性组合案例。任何未完成的内容不得混入默认牌池。

## 8. P4：神牌与选修课

- [ ] 确认神牌的选取/获得方式、阵营、出生与属性。
- [ ] 实现神牌死亡触发、觉醒、保命、复活和连锁死亡，验证不会提前结束对局。
- [ ] 确认课程获得方式、数量、费用、冷却起点、持续时间及“天道伤害”定义。
- [ ] 实现课程技能与被动，处理半点生命、百分比伤害/减免和取整顺序。
- [ ] 处理无生命上限、指定/自定义判定、未知出生地和相关特殊规则。
- [ ] 核对神牌/课程与普通角色、装备、天灾及胜利条件的组合。

验收：所有已启用神牌/课程的代表性完整对局通过原作者核对；复活后排名、同时死亡及连续触发有明确结果，没有无限重复触发。暂未确认的内容继续隔离。

## 9. P5：体验完善与发布准备

- [ ] 根据实际目标完成手机/平板布局、手牌阅读、目标选择和响应操作。
- [ ] 优化素材尺寸、缩略图、加载与错误提示，保留原图详情。
- [ ] 完成规则图鉴、操作引导、连接状态与结果页。
- [ ] 完成范围冻结后的规则、联机及浏览器回归。
- [ ] 邀请原作者和朋友实际试玩，记录缺陷与平衡建议；规则调整单独确认。
- [ ] 准备生产构建、运行配置、HTTPS/WSS、状态保存、备份/恢复与部署说明。
- [ ] 完成候选版本验收，确认发布目标后开展对外发布与发布后核验。

交付：可运行源码、启动/部署入口、操作说明、启用内容表、测试与试玩报告、发布候选包。

“构建完成”“本地验证通过”“真实试玩通过”“对外发布”分别登记。只有实际完成的事项标为通过，未进行的项目写“待验收”。

目前可推进的准备工作：资料转录、素材登记、规则差异表、地图标注草案、首版候选清单和验收场景整理。对于缺失规则，可以提出带理由的建议值或算法，但必须标记为草案；不得默认为原作规则或直接进入正式牌池。

开发阶段按实际授权推进，不因单个高级规则未定停止所有独立工作。不得静默新增玩法、删掉角色技能或修改卡牌数值。若进入开发，发现现有项目已有新代码或用户改动，应先复核当前状态再更新进度。
